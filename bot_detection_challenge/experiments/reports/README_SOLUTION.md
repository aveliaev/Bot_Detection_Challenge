# Bot detection — решение и отчёт об исследовании

> **Примечание.** Этот файл описывает решение **цикла 1** (бленд, `solution/train_final.py`). Итоговое решение — модель B0 (`solution/train_final_v2.py`); его описание и обзор всех экспериментов — в [`FINAL_REPORT.md`](FINAL_REPORT.md).

**Файл для проверяющей системы:** `submission.csv` (`cookie_id,score`, 4909 строк, по одной на каждую cookie из test).

**Воспроизведение:** `pip install -r requirements.txt && python solution/train_final.py` (Python 3.11.15, около 2 минут на 4 CPU).

## 1. Данные (главное)
| | train | test | events |
|---|---|---|---|
| строк | 11 091 cookie (899 ботов, 8.1%) | 4 909 cookie | 328 905 |
| окна | 06.04–19.04 | 20.04–26.04 | 06.04–26.04 |

- Каждое окно — календарные сутки. Test **строго позже** train по времени. Пересечений cookie между train и test нет.
- **Утечка №1:** в train есть 40 779 событий **после** `window_end_ts` (у ботов 42% событий, у людей 11%). В test таких событий нет. Всё, что вне окна, выброшено.
- **Утечка №2:** `captcha_shown` (eid 900) встречается **только после окна** (441 из 899 ботов). Признак не используется (гипотеза H10: сигнал сильный, но это утечка).
- Регистр в `platform` (`WEB/Web/web/desktop`, `ANDROID/Android/android` и т.п.) меняется случайно от события к событию. Это технический шум: после нормализации у каждой cookie ровно одна платформа.
- Около 1.5% строк — точные дубликаты. Их доля одинакова в train и test, а число дубликатов пропорционально числу событий (технический артефакт). Дубликаты удалены.
- Строки файла не отсортированы: сортирую по `(cookie_id, event_ts, eid)`.

## 2. Найденные закономерности (бот vs человек)
1. **Пул item у ботов (самый ценный сигнал из найденных).** Боты берут `item_id` из общего устойчивого пула: 52% item, которые боты смотрели во второй неделе, уже встречались у ботов первой недели, у людей таких 9%. Число *других ботов*, смотревших те же item, даёт AUC 0.80, число людей — 0.56. Поисковые запросы, категории и города пула не образуют: разброс укладывается в биномиальный шум.
2. **Pointer:** у людей координаты равномерны по 1920×1080. У ботов они сжаты в центральный прямоугольник (x < ~1250 у 90% событий против 63% у людей), плюс ровно 0 и края 1080/1920. Web-cookie совсем без pointer — боты в 18% случаев против ~6% у остальных.
3. **Интервалы:** у ботов 58% интервалов внутри сессии попадают в 3–20 с (у людей 20%). Интервалов 0–2 с у ботов *меньше*, похоже на `sleep(random)` с минимальной задержкой. Интервалы регулярнее: ниже `dtexact_uniq_ratio` и std логарифма интервала.
4. Боты смотрят больше разных городов и категорий и чаще переключаются между ними, уходят глубже по страницам выдачи (среднее 3.7 против 2.0) и чаще повторяют запрос. Их cookie моложе (медиана 3 дня против 62).
5. **User-Agent почти бесполезен.** Скрейперские библиотеки (curl, Scrapy, python-requests) — лишь 19–27% ботов, char TF-IDF по UA даёт P@R 0.12 при базовой доле 0.081. Это «технические», а не поведенческие признаки.
6. Каждое семейство признаков по отдельности слабое (P@R 0.31–0.61), а вместе дают 0.88+. Сигнал сидит во **взаимодействиях** признаков.

## 3. Валидация
- `dayblock` (**основная**): 6 фолдов, каждый — 2 дня валидации (дни 2–13); дни 0–1 всегда в обучении.
- `fwd7` (**test-подобная**): обучение на днях < k, валидация на следующих 7 днях без их меток (k=5, 7). Точно воспроизводит разрыв test в 1–7 дней от последней метки.
- `strat` (StratifiedKFold) — для сравнения; даёт близкие числа, значит сильного временного дрейфа нет.
- Признаки пула считаются **внутри каждого фолда** только по меткам обучающей части и только по дням строго раньше дня cookie.
- **Adversarial validation:** без признаков популярности и пула AUC train/test = 0.51 (сдвига нет). Первая версия популярности давала 0.995: нормировка на число cookie за день клала значения на решётку, уникальную для каждого дня. После перехода на сырые счётчики, фиксированное 7-дневное окно истории и константный prior осталось 0.67–0.74. Остаток — реальный эффект: item живут около 8 дней, и доля «известных» item у test ниже. `fwd7` показывает, что пул переносится: P@R 0.877 при разрыве 1–3 дня и 0.866 при 4–7.
- Решения принимались по OOF P@R на обеих схемах и по устойчивости по фолдам и seed. Шум метрики около ±0.013, поэтому разницы < 0.02 значимыми не считались.

## 4. Метрика
Используется официальный `metric.py`. `solution/metrics.py` содержит независимую реализацию через `np.unique` и тесты: ties, немонотонный пример, 2000 случайных проверок на равенство реализаций и на инвариантность к перестановке строк.

## 6. Ablation (LightGBM, все признаки минус семейство, 3 seed, dayblock; всё вместе = 0.881)
Без pointer — **0.831**, без pool — **0.855**, без интервалов — 0.875, без items — 0.877, без популярности — 0.880. Удаление остальных семейств (activity, events, sequence, search, UA, time, missing, lastN, cookie age) даёт 0.882–0.890, то есть в пределах шума: они избыточны. Отсюда отбор топ-120 признаков по важности CatBoost.
Проверка гипотез:
- **H7 (pointer), H2/H3 (интервалы и их регулярность), H5 (items), пул** — подтверждены.
- **H1, H6, H11, H12, H13** — есть сигнал, но избыточный.
- **H8 (UA), H9 (missingness), H14 (последние N минут)** — не подтверждены.
- **H10 (captcha)** — утечка.
- **H15 (сдвиг)** — найден и устранён в признаках популярности и пула.

## 7. Ошибки около Recall = 0.70 (финальный бленд, OOF dayblock)
- Рабочая точка: precision 0.896, recall 0.703, **606** cookie помечены ботами; TP 543, FP 63, FN 229.
- По сегментам: на web P@R внутри сегмента 0.905, на android 0.578, на iOS 0.181. Пропущенные боты — в основном mobile (нет pointer) и cookie с ≤ 8 событиями (recall 9% при 1–3 событиях).
- FP около порога по профилю совпадают с TP: быстрые интервалы, 9 городов, item из пула, cookie 6 дней, сжатый pointer. 51% из них моложе 7 дней против 21% у TN. Скорее всего, это неразмеченные боты или шум в метках, а не исправимая ошибка ранжирования. Взвешивание классов и отбор признаков здесь не помогли.

## 8. Важность признаков (CatBoost, сумма по фолдам; `work/cat_importance.csv`)
Топ: `ptr_x_std`, `ptr_x_max`, `pool_nb_ge1_frac`, `sdt_q90`, `ptr_exact_edge_frac`, `ptr_dist_mean`, `pool_nb_ge1_cnt`, `frac_contact`, `cat_nuniq`, `pool_llr_sum`.
По семействам: интервалы > pointer > items > activity > sequence > events > pool > search.

## 9. Архитектура
```
events.csv.gz -> только события в окне, dedup, сортировка
  -> features.py  : ~300 поведенческих признаков на cookie (только свои события cookie)
  -> history.py   : популярность item (другие cookie, дни [D-6, D]) и пул ботов
                    (метки cookie за дни [E-7, E-1], E = min(D, последний размеченный день + 1))
  -> топ-120 признаков (solution/feature_list.json)
  -> CatBoost(d6, lr .03, 1500 it) ×5 seed, ExtraTrees(leaf 3) ×5, XGBoost(d4) ×5
  -> rank-average с весами 0.6 / 0.2 / 0.2 -> min-max в [0, 1] -> submission.csv
```
Веса бленда подобраны по OOF (сетка с шагом 0.1). Поверхность весов плоская, поэтому выбрана гладкая точка, а не максимум.

## 10. Random state
Все модели используют `seed ∈ {0,1,2,3,4}` (CatBoost `random_seed`, XGBoost/ExtraTrees `random_state`). StratifiedKFold `random_state=0`. Схемы по дням детерминированы. Многопоточные суммы CatBoost/XGBoost при повторном запуске дают расхождение score до 4e-5, на порядок cookie это практически не влияет.

## 11. Соблюдение правил
Нет внешних API и LLM, нет ручной разметки, нет hardcode `cookie_id`, `cookie_id` не используется как признак. Для test используются только метки train (все они раньше test) и неразмеченные события test за дни ≤ дня cookie.
