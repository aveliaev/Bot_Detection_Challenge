## 1. Подход

1. **Очистка событий.**
   - Берём только события внутри окна наблюдения cookie `[window_start_ts, window_end_ts)`.
   - Удаляем точные дубликаты.
   - Сортируем по времени.
2. **Около 115 поведенческих признаков** по событиям самой cookie: курсор, паузы, сессии, набор событий и переходов, объявления / категории / города, поиск, User-Agent.
3. **Признаки по объявлениям на основе других cookie** — строго по прошлому:
   - *популярность*: сколько других cookie смотрели те же объявления за последние 7 дней (без меток);
   - *пул объявлений ботов*: сколько размеченных ботов и людей смотрели те же объявления. Используются только метки более ранних дней.
4. **CatBoost** (1500 деревьев, глубина 6) × 5 seed, среднее рангов, приведение score к [0, 1].

## 2. Валидация и насколько она соответствует задаче

Test лежит строго позже train: train — 06.04–19.04, test — 20.04–26.04, то есть 1–7 дней после последней метки. Поэтому случайный KFold не подходит, валидация только по времени:

- **Повторная day-block CV (P0–P4).**
  - 12 дней (2–13) разбиваются на 6 блоков по 2 дня; каждый блок по очереди — валидация, остальное — обучение.
  - 5 разных разбивок дней: разброс между ними показывает шум метрики, около ±0.004.
  - Дни 0–1 всегда в обучении, пулу объявлений нужна размеченная история.
- **fwd7 — проверка «как test».** Обучаемся на днях < k и проверяем на следующих 7 днях (k = 5, 7). Воспроизводит разрыв 1–7 дней между последней меткой и test.
- **Признаки, зависящие от меток,** пересчитываются внутри каждого фолда только по меткам обучения и только по дням строго раньше дня cookie.
- **Метрика** — официальная `metric.py`.

Кроме этого, в исследовании (`experiments/research2/`) были:
- unit-тесты на утечки;
- adversarial validation train против test;
- paired bootstrap «кандидат против baseline».

Кандидат принимался, только если он лучше и на повторной CV, и на fwd7 сверх шума.

## 4. События и временные окна
- **Окна.** У каждой cookie своё окно наблюдения длиной в сутки. В train есть **40 779 событий после `window_end_ts`**: у ботов 42% событий, у людей 11%, среди них `captcha_shown`. В test таких событий нет, значит это утечка метки. Все события вне окна выброшены, `captcha_shown` не используется.
- **Порядок событий.** Строки файла не упорядочены: сортируем по `(cookie_id, event_ts, eid)`, `eid` разрешает одинаковые метки времени.
- **Паузы.** Паузы и сессии (разрыв > 30 минут) считаются только внутри окна одной cookie.
- **Признаки по другим cookie** строго причинные:
  - популярность — события других cookie за дни [D−6, D] без меток;
  - пул ботов — только метки дней строго раньше D; для test это метки train.

## 5. Пропуски, дубликаты, категориальные признаки
- **Дубликаты.** Около 1.5% строк — точные дубликаты. Их доля одинакова в train и test, а число пропорционально активности cookie, то есть это технический артефакт логирования. Удалены.
- **Пропуски.** Пропуск часто сам по себе информативен: у web-cookie нет курсора у 18% ботов против ~6% остальных; нет поиска; одно событие — нет пауз. Поэтому пропуски **не заполняются**: признак остаётся NaN, CatBoost обрабатывает его отдельной веткой. Явно заданы только флаги вроде `ptr_none_web` — web-cookie без курсора.
- **Категориальные признаки.** `event_name`, `item_category`, `item_location`, `seller_type`, `search_query`, `user_agent` не кодируются напрямую: высокая кардинальность, категории и города меняются от недели к неделе, «кампании» по категориям оказались шумом. Вместо этого на уровне cookie считаются:
  - доли событий и переходы между ними;
  - число уникальных значений, энтропия и доля самого частого;
  - частота переключений между городами и категориями;
  - для User-Agent — длина, версия браузера или приложения и редкость.
- **`platform`.** Регистр меняется от события к событию (`WEB/Web/web/desktop`) — технический шум, значения приводятся к нижнему регистру.
- **Единственное «кодирование по метке»** — пул объявлений, и оно строго по прошлым дням.

## 6. Признаки и почему именно они
Каждое семейство следует из EDA (`experiments/work/`). Вклад измерен ablation: убираем семейство и смотрим падение P@R.

| семейство | что видно в данных | вклад |
|---|---|---|
| **курсор** | у людей координаты равномерны по 1920×1080; у ботов сжаты в центральный прямоугольник (x < ~1250 у 90% событий против 63%) и часто попадают точно в 0 и на края 1080 / 1920 | без него −0.084 |
| **пул объявлений ботов** | боты берут объявления из общего устойчивого пула: 52% объявлений ботов второй недели уже были у ботов первой, у людей 9%; число *других ботов* на тех же объявлениях — AUC 0.80 | без него −0.029, на fwd7 −0.070 |
| **паузы** | у ботов 58% пауз внутри сессии попадают в 3–20 с (у людей 20%), пауз 0–2 с у ботов *меньше* (минимальная задержка скрипта), паузы регулярнее | крупный, частично дублируется |
| **объявления, города, категории, поиск** | боты смотрят больше городов и категорий, чаще переключаются, глубже листают выдачу (средняя страница 3.7 против 2.0), cookie моложе (медиана 3 дня против 62) | средний |
| **User-Agent** | скрейперские библиотеки (curl, Scrapy, requests) — только у 19–27% ботов | слабый, контекст |

- **Отбор признаков.** Из ~300 признаков-кандидатов оставлены 115 лучших по важности CatBoost плюс признаки пула. Удаление слабых семейств метрику не меняло.
- **Сигнал во взаимодействиях.** По отдельности каждое семейство слабое (P@R 0.31–0.61), вместе — 0.90.

## 7. Что пробовали и что не получилось
После финальной модели было ещё 6 циклов исследования с поиском нового сигнала. Все эксперименты, числа и причины — в `experiments/README.md`, кратко:

| направление | лучший результат против 0.900 / fwd7 0.902 |
|---|---|
| другие модели (LogReg, ExtraTrees, XGBoost, LightGBM), тюнинг, бленды | 0.82–0.903, в пределах шума |
| граф cookie ↔ объявление, вероятность бота для объявления | 0.898–0.901 — повтор пула |
| отдельные модели web / mobile, второй этап на трудных примерах, ранжирование | 0.890–0.901 |
| поиск «сервисов» ботов: кластеры, прототипы, multiclass | 0.889–0.895 |
| отдельные детекторы по каналам + слияние (Iliou et al., 2021) | 0.892 / 0.886 |
| переранжирование около порога | 0.893 / 0.899 |
| self-supervised задачи, межканальные остатки | +0.001–0.002 при −0.006…−0.012 на fwd7 |
| окна событий, кинематика курсора, LSTM / BiLSTM (ISIT 2024) | 0.899 / 0.884; LSTM сама по себе 0.59 |

По пути нашли и исправили несколько «ложных улучшений», которые дали бы красивую валидацию и провал на test:
- признаки популярности и накопления свидетельств различали train и test с AUC 0.995 («решётка значений» по дням);
- признаки по UA различали train и test с AUC 1.0;
- в одном из вариантов LLR метки дня косвенно попадали в признаки.

## 8. Ограничения модели
- **Потолок около 0.90.** На рабочей точке TP 545, FP 59, FN 227. 45 из 59 FP — cookie с меткой «человек», которые все модели ставят в топ. У них тот же генератор курсора и тот же пул объявлений, что у ботов; отличаются только более человеческими паузами. Ни один из 7 циклов не отделил их от ботов лучше AUC 0.65. Это либо автоматизация вне списка «известных сервисов», либо шум разметки — по этим данным не различить. Метки не менялись.
- **Mobile.** P@R внутри android около 0.57, iOS около 0.18 (в web около 0.90). Курсора нет, событий мало.
- **Короткие cookie.** Recall при 1–3 событиях около 9%.
- **Зависимость от свежих меток.** Пул объявлений требует размеченной истории за последние 7 дней. Объявления живут около 8 дней, поэтому при большом разрыве между обучением и применением модель ослабнет: на fwd7 без пула −0.07. Модель нужно регулярно переобучать.
- **Чем поднять качество — новыми данными, а не моделями:** сетевые атрибуты (IP / ASN, TLS), серверная телеметрия, touch и сенсоры для mobile, метки «какой сервис».

## 9. Соблюдение правил
- **Данные.** Используются только выданные данные; нет внешних API, LLM, ручной разметки и ручного просмотра test.
- **`cookie_id`.** Только ключ для соединения таблиц: не признак и нигде не захардкожен.
- **Метки.** Не менялись. Метки train используются только для прошлых дней относительно cookie, у test меток нет вообще.
- **Утечки.** События после окна и `captcha_shown` исключены.
- **Выбор модели** — только по валидации. Результат на test для выбора не использовался.
- **Воспроизводимость.** Все seed зафиксированы, результат воспроизводится бит-в-бит.
